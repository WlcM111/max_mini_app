# ADR-008. Способ взаимодействия с MAX

**Вопрос.** Как получать события бота и отправлять сообщения?

**Требования.** Не проектировать MAX по аналогии с Telegram/VK; официальные ограничения: production — только webhook на 443 с доверенным сертификатом, 30 rps на API, 2 сообщения/с на чат (F-42…F-50); токен только в одном сервисе.

**Варианты.**

| Вопрос | Варианты | Решение |
|---|---|---|
| Получение событий | Long Polling; Webhook | Webhook. Long Polling официально не подходит для production и несовместим с активной подпиской |
| Клиент Bot API | официальная Go-библиотека (dev.max.ru/docs/chatbots/bots-coding/go); собственный тонкий клиент на `net/http` | собственный клиент: используются 4 метода (`GET /me`, `GET/POST /subscriptions`, `POST /messages`), нужен полный контроль таймаутов, пула доверия с сертификатом Минцифры и классификации ошибок |
| Кнопка открытия приложения | `open_app` (поля не описаны официально, X-01); `link` с официальным диплинком (F-05) | `link` по умолчанию, `open_app` — флаг `BOT_OPEN_APP_BUTTON_KIND` после MAX-02 |
| Локальная разработка без токена | заглушка | `BOT_MODE=stub` |

**Решение.** Сервис `bot` — единственная точка работы с Bot API: webhook `POST /max/webhook` с проверкой `X-Max-Bot-Api-Secret`, очередь `bot.outbound_messages`, глобальный лимит 20 rps и 600 мс на получателя, восстановление подписки каждые 10 минут. Детали — [MAX integration spec](../max/max-integration-spec.md).

**Основания.** Все решения опираются на официальные факты; неописанные поля не используются по умолчанию.

**Недостатки.** Webhook требует публичного HTTPS-домена уже для проверки на реальном MAX — стенд нужен с первого дня (INF-01).

**Последствия.** Edge маршрутизирует `/max/webhook` на `bot`; в образ `bot` встраиваются сертификаты Минцифры.

**Проверка.** AC-MAX-05…AC-MAX-08; T-GRPC-*, T-BOT-*.

**Условия пересмотра.** Официальное описание `open_app`; появление в MAX серверных push-API для мини-приложений.
