# ADR-016. Режим проверки и демо-данные

**Вопрос.** Как проверяющие получат доступ к API с ролями без MAX и без «чёрного хода»?

**Требования.** Кейс: тестовые учётные записи для ролей, DATA-API.yaml, первый служебный слайд презентации; безопасность.

**Варианты.** A. Статические токены в переменных окружения — легко утечь, нельзя отозвать. B. Endpoint входа по паролю — новая поверхность атаки. C. CLI-команда внутри контейнера `core`, выпускающая сессию для служебного аккаунта `kind='review'`.

**Решение.** C. `core review-token issue --login <login> --role <editor|viewer> --ttl 336h` создаёт (или находит) аккаунт `review`, добавляет его в демо-организацию с указанной ролью и печатает токен `vvs_…` один раз; `core review-token revoke --login <login>` отзывает сессии. `core seed-demo` создаёт демо-организацию `0b6f2c1e-5a3d-4c8e-9f21-7d4a6b8c9e01` «Кафе «Пример» (тестовые данные)» с 12 документами, включая документ `3c9e7a52-1f4b-4d6a-8e2c-5b7f9a1d3e02`. Названия демо-данных содержат пометку «(тестовые данные)».

**Основания.** Доступ выдаётся только тем, у кого есть доступ к серверу; токены отзываемы; в репозитории их нет.

**Недостатки.** Проверяющий-«review» не проходит путь запуска из MAX — этот путь проверяется в самом MAX тестовыми логинами команды.

**Проверка.** `scripts/run_data_api_checks.py` с токенами ролей проходит все проверки DATA-API.yaml.

**Условия пересмотра.** Организаторы предоставят собственные тестовые аккаунты MAX.
