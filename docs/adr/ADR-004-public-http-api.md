# ADR-004. API между frontend и backend

**Вопрос.** Как frontend обращается к backend?

**Требования.** Frontend не ходит в gRPC; публичный API без отдельного сервиса-шлюза; кейс требует `openapi.yaml`; работа во встроенном окне MAX (возможны ограничения cookie третьих сторон); проверяющие вызывают API по DATA-API.yaml.

**Варианты.** A. REST/JSON в `core` с OpenAPI 3.1. B. gRPC-Web/Connect — требует прокси или отдельного протокола, плохо описывается OpenAPI. C. GraphQL — лишний слой, сложнее кэширование и авторизация по полям.

**Решение.** A. Базовый путь `/api/v1`, тот же origin, что и статика (CORS не нужен). JSON snake_case, даты `YYYY-MM-DD`, время RFC 3339 UTC. Ошибки — `application/problem+json` с кодом `ErrorCode`. Аутентификация — `Authorization: Bearer vvs_…`. Создание ресурсов идемпотентно по клиентскому UUID. Оптимистичная блокировка — `expected_version`. Пагинация — курсор. Единственный источник — `openapi.yaml` в корне репозитория (владелец B).

**Основания.** Кейс прямо требует OpenAPI; REST проверяется curl-ом по DATA-API.yaml; токен в заголовке не зависит от политики cookie во встроенном окне.

**Недостатки.** Типы frontend генерируются из OpenAPI, а backend-обработчики пишутся вручную — расхождение ловится контрактными тестами.

**Последствия.** Контрактный тест `core`: каждый ответ обработчика валидируется по схеме OpenAPI (kin-openapi) в тестах API. Изменения — только добавление необязательных полей и новых путей в пределах `v1`.

**Проверка.** T-API-*, контрактный тест, проверки DATA-API.yaml (`scripts/run_data_api_checks.py`).

**Условия пересмотра.** Появление второго клиента с потоковыми данными.
