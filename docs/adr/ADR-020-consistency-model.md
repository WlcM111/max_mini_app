# ADR-020: Модель согласованности между core и reminders

Статус: принято. Дата: 2026-09-20. Версия архитектуры: 2.0.0.
## Контекст
В v1.0.0 изменение документа и перестроение плана выполнялись одной транзакцией.
После разделения общая транзакция невозможна: распределённые транзакции не применяются.

## Рассматриваемые варианты
1. Синхронный вызов core → reminders внутри транзакции core. Транзакция удерживается на время сетевого вызова, отказ reminders блокирует изменение документа.
2. Транзакционный outbox в core + доставка по gRPC + идемпотентная обработка в reminders.
3. Брокер сообщений. Запрещён ограничениями проекта без доказанной необходимости.

## Решение
Вариант 2. Изменение и запись события в outbox — одна транзакция core (durable acceptance).
Доставка — отдельный процесс-relay по gRPC. Обработка в reminders идемпотентна по `event_id`,
устаревшие версии агрегата отбрасываются.

Для сохранения пользовательской семантики AC-05 core после фиксации транзакции выполняет
синхронную попытку доставки с ограниченным сроком (`CORE_REMINDERS_SYNC_FLUSH_TIMEOUT`, 300 мс).
Успех — ответ API содержит актуальный план; неуспех — ответ помечается как «пересчёт выполняется»,
и доставка продолжается в фоне.

## Основания
Запись в outbox даёт гарантию неутраты задания при отказе reminders.
Синхронная попытка сохраняет привычное поведение интерфейса в обычном режиме.

## Недостатки
Появляется окно рассогласования при недоступности reminders; API возвращает состояние синхронизации,
которого не было в v1.0.0.

## Последствия
- Гарантии: durable acceptance, at-least-once доставка, идемпотентная обработка, порядок в пределах агрегата.
- Exactly-once не обещается.
- Запись в outbox не считается доставкой события: состояние доставки хранится в самой записи.

## Условия пересмотра
Требование строго немедленного пересчёта на стороне продукта — возврат плана в core.
