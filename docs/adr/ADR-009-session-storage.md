# ADR-009. Хранение сессии

**Вопрос.** Как хранить аутентификацию между запросами?

**Требования.** Работа во встроенном окне всех клиентов MAX; `DeviceStorage`/`SecureStorage` не работают в веб-версии (F-24); отзыв сессий; без секретов во frontend.

**Варианты.** A. Cookie `HttpOnly` — во встроенном окне веб-клиента возможны ограничения cookie третьих сторон (не подтверждено, U-06). B. JWT без хранения — нельзя отозвать до истечения, ключ подписи — ещё один секрет. C. Непрозрачный токен `vvs_` + 32 случайных байта (base64url), в БД хранится SHA-256 токена; клиент хранит токен в памяти и `sessionStorage`. D. `SecureStorage` MAX — нет в веб-версии.

**Решение.** C. Срок жизни 12 ч (`CORE_SESSION_TTL`), `last_seen_at` обновляется не чаще раза в 5 минут; выход — `DELETE /sessions/current`; удаление аккаунта отзывает все сессии. При 401 frontend один раз пытается создать новую сессию по `initData`; если данные запуска старше часа — просит перезапустить приложение.

**Основания.** Не зависит от политики cookie; отзыв мгновенный; хеш в БД бесполезен при утечке базы.

**Недостатки.** Запрос к БД на каждую аутентификацию (индекс по `token_hash`, < 1 мс); токен в `sessionStorage` доступен скрипту страницы — снижается строгим CSP без `unsafe-inline` для скриптов.

**Последствия.** Таблица `core.sessions`; чистка просроченных сессий фоновой задачей раз в час.

**Проверка.** T-API-SESSION-*, T-SEC-02 (отозванный токен → 401).

**Условия пересмотра.** Подтверждение, что cookie надёжно работают во всех клиентах MAX.
