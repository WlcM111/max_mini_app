# ADR-002. Границы микросервисов

**Вопрос.** Сколько backend-сервисов и где проходят их границы?

**Требования.** Микросервисы с минимальным числом сервисов; внутри — слоистая архитектура; межсервисно только gRPC; frontend не ходит в gRPC; без отдельного API Gateway; единственный держатель токена бота; 2 разработчика.

**Варианты.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Монолит | проще | нарушает требование микросервисов; токен бота в том же процессе, что и публичный API |
| B. Два сервиса: `core` (публичный HTTP API + предметная логика + планировщик) и `bot` (всё взаимодействие с MAX Bot API) | граница по внешней системе и по секрету; независимые отказы; по одному владельцу на сервис | один gRPC-контракт и одна сетевая зависимость |
| C. Четыре сервиса: gateway, documents, reminders, bot | «чистые» домены | распределённые транзакции между документами и напоминаниями, лишние контракты, API Gateway запрещён без обоснования |

**Решение.** Вариант B.

| Сервис | Ответственность | Данные | Интерфейсы |
|---|---|---|---|
| `core` | сессии и идентификация по initData, организации, участники, приглашения, справочник, документы, периоды, план напоминаний, планировщик, экспорт ICS | схема `core` | HTTP `:8080` (через edge), admin `:8081`; gRPC-клиент к `bot` |
| `bot` | webhook MAX, состояние диалогов, очередь исходящих сообщений, ограничение скорости, подписка, профиль бота | схема `bot` | gRPC `:9090`, HTTP webhook `:8080` (через edge), admin `:8081` |

**Основания.** Напоминание рождается из изменения документа — документ и план напоминаний меняются в одной транзакции `core`. Граница с `bot` проходит по внешней системе MAX со своими лимитами (30 rps, 2 msg/s на чат) и по секрету (токен бота). Отказ MAX не влияет на работу реестра документов.

**Недостатки.** Доставка напоминания пересекает границу сервисов: нужна идемпотентная передача (ADR-010).

**Последствия.** Один `.proto` (владелец A), один OpenAPI (владелец B). Прямых вызовов bot → core нет: bot не знает о документах.

**Проверка.** Отчёт согласованности, проверки 8–10; тест: остановка `bot` не ломает CRUD документов (NFR-T05).

**Условия пересмотра.** Появление второго канала доставки (email/SMS) — тогда `bot` превращается в `notifier` с тем же контрактом; нагрузка core > 1 000 RPS — выделение планировщика.
