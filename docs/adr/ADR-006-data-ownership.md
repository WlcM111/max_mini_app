# ADR-006. Владение данными и экземпляр PostgreSQL

**Вопрос.** Как разделить данные двух сервисов?

**Требования.** PostgreSQL; без межсервисных транзакций и FK между схемами; обоснованный один экземпляр; ограниченные ресурсы одного хоста.

**Варианты.** A. Отдельный экземпляр PostgreSQL на сервис. B. Один экземпляр, отдельная база на сервис. C. Один экземпляр, одна база `vovremya`, схемы `core` и `bot`, у каждого сервиса свои роли `*_migrator` (владелец схемы) и `*_app` (DML), без прав на чужую схему.

**Решение.** C.

**Основания.** Нагрузка целевого профиля (≈ 375 запросов к БД в секунду, 8,5 ГБ данных, см. [load-reliability.md](../architecture/load-reliability.md)) укладывается в один экземпляр с запасом; второй экземпляр удвоил бы память и резервное копирование без выигрыша в отказоустойчивости на одном хосте. Изоляция обеспечивается привилегиями: `core_app` не имеет `USAGE` на схему `bot` и наоборот.

**Недостатки.** Общий отказ БД затрагивает оба сервиса; общий пул соединений экземпляра (`max_connections=100`).

**Последствия.** Связь между данными сервисов — только через gRPC и значения идентификаторов (`max_user_id`, `idempotency_key`). Роли создаёт `deploy/postgres/init/01-init.sh`; справочники `core` доступны `core_app` только на чтение.

**Проверка.** T-REPO-ISO: подключение ролью `core_app` и `SELECT` из `bot.outbound_messages` завершается ошибкой `permission denied for schema bot`.

**Условия пересмотра.** Требование отказоустойчивости БД — вынос в управляемый PostgreSQL с репликой.
