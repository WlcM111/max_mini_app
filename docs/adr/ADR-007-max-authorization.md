# ADR-007. Авторизация через MAX

**Вопрос.** Как backend узнаёт, кто открыл мини-приложение?

**Требования.** Проверка MAX identity на backend по реальному механизму; freshness; replay protection; frontend — недоверенная среда; никаких секретов во frontend.

**Факты.** MAX передаёт подписанные данные запуска `initData`; алгоритм HMAC-SHA256 с ключом `HMAC-SHA256("WebAppData", BOT_TOKEN)`; рекомендуемый срок — 1 час (F-09…F-14).

**Варианты.** A. Проверять подпись в `core`, имея токен бота. B. Проверять в `bot` через gRPC — лишний синхронный вызов на каждый вход, отказ bot блокирует вход. C. Проверять в `core` производным ключом без токена.

**Решение.** C. `core` получает `CORE_MAX_WEBAPP_SECRET_HEX` = `hex(HMAC-SHA256("WebAppData", BOT_TOKEN))` — это ровно `secret_key` алгоритма. После проверки создаётся серверная сессия (ADR-009). Алгоритм и дополнительные проверки — [MAX integration spec, раздел 4](../max/max-integration-spec.md#4-проверка-данных-запуска-на-backend).

**Основания.** Производный ключ позволяет проверить подпись, но не позволяет вызвать Bot API: компрометация `core` не даёт отправлять сообщения от имени бота. Вход не зависит от доступности `bot`.

**Недостатки.** При смене токена бота нужно пересчитать ключ и перезапустить `core` (скрипт `scripts/derive_webapp_secret.py`).

**Последствия.** Защита от повтора — срок 1 ч, допуск будущего времени 60 с, лимиты создания сессий; `initData` не логируется.

**Проверка.** Тест-векторы TV-1…TV-6 (T-DOM-AUTH), AC-MAX-02, AC-MAX-03.

**Условия пересмотра.** MAX изменит алгоритм подписи или опубликует серверную проверку через API.
