# Нагрузка, масштабирование и надёжность

Версия 1.0.0 · 20.09.2026

## 1. Профили нагрузки

Допущения модели (A-08): 1,5 открытия мини-приложения на активного пользователя в сутки; 11 API-запросов на открытие (5 при запуске: `sessions`, `me`, `catalog`, `organizations/{id}`, `documents`; 6 действий); 15 % суточных запросов приходится на пиковый час; минутный коэффициент пика 2,5; у организации 15 документов, 3 отступа, 1,3 получателя напоминаний; 60 % напоминаний приходится на окно 09:00–09:30 МСК; 30 % получателей открывают мини-приложение из напоминания.

| Величина | Формула | P1 демо и проверка | P2 пилот (СПб) | P3 целевой |
|---|---|---|---|---|
| Организации | — | 10 | 2 000 | 200 000 |
| Пользователи | — | 30 | 3 000 | 300 000 |
| Активные в сутки (DAU) | доля 25 % (P2), 20 % (P3) | 30 | 750 | 60 000 |
| Открытий в сутки L | DAU × 1,5 | 45 | 1 125 | 90 000 |
| Запросов в сутки Q | L × 11 | 495 | 12 375 | 990 000 |
| Средний RPS пикового часа | Q × 0,15 / 3600 | 0,02 | 0,52 | 41,3 |
| Пиковый RPS | × 2,5 | 10 (одновременная проверка) | 1,3 | 103 |
| Напоминаний в сутки R | орг × 15 × 3 × 1,3 / 365 | 2 | 320 | 32 054 |
| Всплеск после напоминаний, RPS | R × 0,6 × 0,3 × 11 / 1800 | 0 | 0,4 | 35,3 |
| **Расчётный пик API** | пик + всплеск, с округлением | **10** | **2** | **150** |
| Цель по ёмкости (запас ×2) | — | 20 | 20 | 300 |
| Запросов к БД в секунду | пик × 2,5 | 25 | 5 | 375 |
| Сообщений бота в окне 09:00–09:30 | R × 0,6 | 1 | 192 | 19 232 |
| Скорость отправки в окне, сообщ./с | / 1800 | 0 | 0,1 | 10,7 (лимит 20) |

Соотношение чтение/запись: 2,5 записи из 11 запросов (создание сессии и 1,5 изменения документа) → 23 % записи, 77 % чтения.

| Таблица | Строк | Байт на строку с индексами | Объём |

| bot.outbound_messages (30 сут) | 960 000 | 800 | 0,8 ГБ |
| прочие (сессии, аудит, участники) | — | — | 0,2 ГБ |

Размеры ответов: список 50 документов ≈ 20 KB JSON (≈ 4 KB gzip); карточка ≈ 3 KB; справочник ≈ 15 KB (≈ 4 KB gzip, кешируется по ETag); тело `POST /sessions` ≈ 1 KB. Трафик P3 в пике: 150 × 5 KB ≈ 0,75 МБ/с ≈ 6 Мбит/с.

Frontend: начальный JS ≤ 200 KB gzip, CSS ≤ 40 KB gzip; при 4G 1,6 Мбит/с и RTT 150 мс: загрузка 240 KB ≈ 1,2 с + разбор ≈ 0,8 с + два API-запроса ≈ 0,4 с → ≈ 2,4 с до первого экрана (цель ≤ 3 с).

## 3. Ресурсы

| Профиль | Хост | PostgreSQL | core | bot |
|---|---|---|---|---|
| P1, P2 | 2 vCPU, 4 ГБ, SSD 40 ГБ | `shared_buffers=256MB`, лимит 1 ГБ | 1 CPU, 256 МБ | 0,5 CPU, 128 МБ |
| P3 | 4 vCPU, 8 ГБ, SSD 80 ГБ | `shared_buffers=2GB`, `effective_cache_size=5GB`, `work_mem=8MB`, лимит 4 ГБ | 2 CPU, 512 МБ | 0,5 CPU, 256 МБ |

Размер пулов по закону Литтла: одновременных запросов к БД = 375 × 0,003 с ≈ 1,1 в среднем; при p99 запроса 50 мс — 375 × 0,05 ≈ 19. Пул `core` — 20 соединений, `bot` — 8; лимит ролей 60 и 20 соединений (init-скрипт). Одновременных HTTP-запросов в `core` в пике: 150 × 0,3 с ≈ 45; предел 256.

## 4. Механизмы устойчивости

| Механизм | Где | Параметры |
|---|---|---|
| Ограничение параллелизма | core HTTP | семафор 256 запросов; сверх — 503 `OVERLOADED`, `Retry-After: 1` |
| | пулы БД | core 20, bot 8; ожидание соединения ограничено контекстом запроса |
| | bot | 4 воркера доставки, пакет 50 |
| Backpressure | bot | очередь > 50 000 строк `queued`/`retry_wait` → `RESOURCE_EXHAUSTED`; core оставляет напоминание `planned` с backoff |
| Rate limiting | core | 10 запросов/с на аккаунт (всплеск 30); `POST /sessions` — 10/мин на пользователя MAX и 300/мин на IP; `client-events` — 60/мин на IP; `invites/preview`, `invites/accept` — 10/мин на аккаунт |
| | bot → MAX | 20 вызовов/с глобально; 1 сообщение в 600 мс на получателя |
| Deadline propagation | core | бюджет обработчика 5 с в `context`; запросы к БД и gRPC получают остаток; gRPC-deadline не больше 2 с |
| | bot | запрос к MAX 10 с; обработчик webhook 10 с |
| Повторы с backoff и jitter | frontend | GET: 2 повтора через 0,5 с и 1,5 с ± 20 %; изменения — без автоповтора, кроме сетевой ошибки при создании (тот же клиентский UUID) |
| | core → bot | `min(5 мин, 10 с × 2^attempts) + U(0; 5 с)` |
| | bot → MAX | `U(0; min(10 мин, 5 с × 2^(n−1)))`, до 8 попыток |
| Идемпотентность | все изменения | клиентские UUID, `idempotency_key`, дедупликация webhook |
| Graceful shutdown | core, bot | SIGTERM → `/readyz` = 503 → HTTP `Shutdown` до 20 с → остановка циклов планировщика и воркеров после текущего пакета → `grpc.GracefulStop` до 5 с → закрытие пула БД; укладывается в `stop_grace_period: 30s` |

## 5. Матрица отказов

| ID | Отказ | Обнаружение | Влияние | Поведение системы | Восстановление | Тест |
|---|---|---|---|---|---|---|
| F-01 | edge остановлен | healthcheck edge, внешняя проверка | мини-приложение и webhook недоступны | MAX повторяет webhook до 8 ч | `restart: unless-stopped`; при > 8 ч SubscriptionKeeper переподписывает | T-FAIL-01 |
| F-02 | core упал или перезапускается | healthcheck, 502 на edge | API недоступен секунды | принятые транзакции сохранены; незафиксированные — нет; напоминания повторятся | автоматический перезапуск | T-NFR-RESTART |
| F-03 | bot недоступен | `vovremya_grpc_client_requests_total{code="Unavailable"}` | нет новых приглашений, статус канала `unavailable`, напоминания ждут | CRUD работает; напоминания `planned` с backoff | после старта bot напоминания передаются | T-FAIL-02 |
| F-04 | PostgreSQL недоступен | `/readyz` 503 | всё недоступно | API 503; webhook 503 (MAX повторит) | перезапуск контейнера; данные на томе | T-FAIL-03 |
| F-05 | Диск БД заполнен | ошибки записи в логах, `df` | запись невозможна | чтение работает, запись 503 | очистка, retention, расширение диска | runbook |
| F-06 | MAX Bot API 5xx или недоступен | `vovremya_max_api_requests_total{status_class="5xx"}` | сообщения не уходят | `retry_wait`, до 8 попыток, `not_after` | автоматически | T-FAIL-04 |
| F-07 | MAX Bot API 429 | `status_class="429"` | замедление доставки | скорость ÷2 на 60 с | автоматически | T-FAIL-05 |
| F-08 | Неверный токен бота (401) | лог error `max_401` | сообщения не уходят | `retry_wait` | заменить токен, перезапустить bot и core (новый производный ключ) | runbook |
| F-09 | Недоступен `st.max.ru` у клиента | `bootstrap_failed{code=not_in_max}` в телеметрии | мини-приложение не запускается | экран «Откройте из MAX» | вне контроля команды | T-E2E-06 |
| F-10 | Истёк или не выпущен сертификат | ошибки ACME в логах edge | HTTPS и webhook недоступны | Caddy повторяет выпуск | проверить DNS и порт 80 | runbook |
| F-11 | Отказ хоста | внешняя проверка | полный простой | резервирования нет (L-01) | восстановление из дампа на новом хосте, RTO ≈ 1 ч, RPO 24 ч | учения REL-02 |
| F-12 | Устаревший или подделанный initData | `session_create_total{result}` | вход отклонён | 401 с понятным экраном | пользователь перезапускает | T-SEC-01 |
| F-13 | Сдвиг часов сервера | NTP хоста | ложные `LAUNCH_DATA_EXPIRED` | допуск 60 с | синхронизация времени хоста | runbook |
| F-14 | Повтор webhook | `webhook_updates_total{result="duplicate"}` | нет | 200 без эффектов | — | T-IDEM-03 |
| F-15 | Сбой core во время передачи напоминаний | lease истёк | задержка ≤ 2 мин | повтор с тем же ключом, bot отвечает `duplicate` | автоматически | T-NFR-RESTART |
| F-16 | Сбой bot во время отправки | `sending` с истёкшим lease | задержка ≤ 90 с, возможен дубль | LeaseReaper → `retry_wait` | автоматически | T-NFR-RESTART |
| F-17 | Перегрузка core | 503 `OVERLOADED` | часть запросов отклонена | клиент повторяет GET | снижение нагрузки, вертикальное масштабирование | T-NFR-LOAD |

Честная оценка: Docker Compose на одном хосте не защищает от отказа хоста, диска и сети дата-центра. Целевая доступность — 99 % в месяц (до 7 ч простоя).

## 6. Масштабирование

| Шаг | Условие | Действие | Изменения кода |
|---|---|---|---|
| 1 | CPU core > 70 % в пике | вертикально до 4 vCPU хоста | нет |
| 2 | > 300 RPS | 2–3 реплики `core` за edge (`reverse_proxy` с несколькими upstream) | нет: сессии в БД, планировщик с `SKIP LOCKED`; лимиты частоты становятся на реплику |
| 3 | > 20 сообщений/с устойчиво | общий лимитер для нескольких `bot` (в PostgreSQL, advisory lock) | да, ADR на замену |
| 4 | > 1 ТБ или требования HA | управляемый PostgreSQL с репликой | конфигурация |

## 7. Отвергнутая инфраструктура

| Компонент | Почему не нужен при P3 | Когда пересмотреть |
|---|---|---|
| Kubernetes | 5 контейнеров на одном хосте; Compose покрывает перезапуск и зависимости | > 3 хостов |
| Брокер сообщений | 32 000 сообщений/сутки, пик 11/с; очередь в PostgreSQL с `SKIP LOCKED` | > 100 сообщений/с или второй потребитель событий |
| Redis / distributed cache | справочник в памяти процесса; сессия — один индексный запрос < 1 мс; лимиты — в памяти одной реплики | > 3 реплик core с требованием точного общего лимита |
| Elasticsearch | поиск по названию внутри организации ≤ 500 документов | поиск по всем организациям |
| ClickHouse | аналитики нет; метрики — Prometheus | продуктовая аналитика по событиям |
| Object storage | файлы не хранятся; ICS генерируется на лету | загрузка сканов документов |
| CDN | статика ≈ 300 KB с immutable-кешем | > 100 000 одновременных пользователей |
| WebSocket | обновления не нужны в реальном времени; уведомления — через бота | совместное редактирование в реальном времени |
| API Gateway | edge только проксирует; авторизация в core | несколько публичных сервисов с разной авторизацией |
