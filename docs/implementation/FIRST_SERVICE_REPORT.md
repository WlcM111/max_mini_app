# Отчёт реализации первого микросервиса

Дата: 20.09.2026. Версия архитектуры: 2.0.0.

## 1. Выбранный сервис и обоснование

Выбран **reminders-service**.

| Критерий | Сравнение вариантов |
|---|---|
| Критический путь | контракты reminders нужны и core (относительно outbox и чтения плана), и bot (порядок вызова). Пока они не зафиксированы кодом, оба разработчика рискуют переделкой |
| Зависимости | reminders зависит только от контракта bot-service, который уже был зафиксирован в версии 1.0.0; core зависит от контрактов reminders, поэтому реализация core первой означала бы работу против непроверенного контракта |
| Риск новой архитектуры | весь новый риск варианта C (журнал входящих событий, проекции, версии агрегатов, перепланирование, аренда, гонки) сосредоточен в reminders. Раннее его снятие обесценивает главную угрозу срока |
| Владение данными | схема reminders не пересекается с существующими; реализация не блокируется переработкой схемы core |
| Автономная проверка | сервис проверяется полностью: события подаются через собственный gRPC, получатель заменяется двойником, работающим по нормативному контракту |
| Трудоёмкость | сопоставима с bot-service и существенно меньше core-service, что позволяет завершить сервис целиком, а не частично |
| Срок сдачи | после этого этапа обе оставшиеся дорожки (core и bot) ведутся параллельно без взаимной блокировки |

Варианты, которые отвергнуты: core-service первым — требует готовых контрактов reminders и даёт
позднее обнаружение ошибок согласованности; bot-service первым — наименьший риск и отсутствие новизны,
не снимает угрозу варианта C и оставляет контракт reminders непроверенным.

## 2. Реализованная функциональность

| Область | Состав |
|---|---|
| Приём событий | ApplyEvents (пакет до 200), идемпотентность по event_id, отбрасывание устаревших версий, отклонение некорректных событий, GetIngestState |
| Проекции | организации, участия, документы, отступы; надгробия при удалении; версии агрегатов |
| Планирование | BuildPlan с учётом пояса организации, локального времени получателя, отступов и допустимого опоздания |
| Перепланирование | документ, организация, смена пояса, настройки уведомлений, добавление и исключение участника, удаление документа, организации, аккаунта |
| Расписание | захват пакета FOR UPDATE SKIP LOCKED с арендой, ограниченная конкурентность, проверка состояния перед отправкой |
| Передача в bot | EnqueueNotification с ключом идемпотентности, текстом, кнопкой диплинка и предельным сроком |
| Повторы и отказы | классификация ошибок gRPC, выдержка с ограничением и случайной добавкой, пропуск при окончательном отказе, пропуск просроченных |
| Запросы плана | GetNextReminders, GetDocumentPlan, GetSyncStatus |
| Очистка | журнал событий и неактивные напоминания по срокам хранения |
| Эксплуатация | конфигурация с проверкой, логи JSON с корреляцией, метрики Prometheus, healthz и readyz, graceful shutdown, миграции up и down |

RPC реализованы полностью: IngestService (2), ReminderQueryService (3), Health (1 через стандартный сервер).

## 9. Что делать следующему разработчику

1. Реализовать bot-service по `docs/handoffs/bot-service-v2.md` (дорожка A).
2. Реализовать core-service по `docs/handoffs/core-service-v2.md`, начиная с модулей и схемы, затем outbox и relay (дорожка B).
3. Для разработки core использовать работающий reminders-service: он принимает события по нормативному контракту.
4. После готовности обоих сервисов выполнить сценарий T-CONS-01 и сквозную проверку по плану.
