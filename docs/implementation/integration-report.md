# Отчёт о взаимодействии reminders-service и bot-service

Дата: 23.09.2026. Проверка выполнена на настоящих процессах обоих сервисов
без Docker: `test/e2e/run.sh`, драйвер сценариев `test/e2e/main.go`.

## 1. Схема проверки

```
  драйвер e2e ──ApplyEvents (gRPC)──▶ reminders-service ──EnqueueNotification (gRPC)──▶ bot-service
       │                                     │                                              │
       │                                     ▼                                              ▼
       │                            схема reminders                                   схема bot
       │                          (роль reminders_app)                              (роль bot_app)
       │                                                                                    │
       └──POST /max/webhook, GET /debug/stub/messages, MessagingService (gRPC)──────────────┘
```

Одна PostgreSQL, две схемы, четыре роли (`bot_migrator`, `bot_app`,
`reminders_migrator`, `reminders_app`). Обращения между сервисами идут только
по gRPC: общих таблиц, межсервисных внешних ключей и общей транзакции нет.
Канал MAX заменён режимом `stub` самого bot-service — это штатный режим сервиса,
а не тестовый двойник: код доставки, формирования кнопок и записи результата
выполняется целиком.

## 2. Что проверено

| № | Сценарий | Ожидание | Результат |
|---|---|---|---|
| 1 | `GetBotProfile` до подачи событий | режим `BOT_MODE_STUB`, ник бота, шаблон диплинка | `@vovremya_local_bot`, `https://max.ru/vovremya_local_bot?startapp={payload}` |
| 2 | `ApplyEvents`: организация, участие, документ | три события `APPLIED` | совпало |

| 5 | Доставка | сообщение в канале MAX с текстом напоминания и кнопкой-диплинком | текст «Через 30 дней заканчивается срок: «Фискальный накопитель…». Организация: Кафе на Неве…», кнопка → `?startapp=doc_3c9e7a52…` |

| 9 | Событие webhook с чужим секретом | `401`, никаких изменений в хранилище | совпало |
| 10 | Повтор того же события webhook | второго приветствия нет | число сообщений не изменилось |
| 11 | Отказ bot-service (процесс остановлен) | вызов bot даёт `UNAVAILABLE`; reminders принимает события и строит план | совпало |

| 13 | Восстановление bot-service | отложенное напоминание передано и доставлено без вмешательства | `HANDED_OFF`, затем `SENT` |
| 14 | Изоляция: `bot_app` → схема reminders | отказ в доступе | отказано |
| 15 | Изоляция: `reminders_app` → схема bot | отказ в доступе | отказано |
| 16 | История миграций для роли приложения | `DELETE` запрещён | отказано |
| 17 | Межсервисные внешние ключи | 0 | 0 |
| 18 | Журналы обоих сервисов | нет секретов и текстов сообщений пользователей | совпадений 0 |

Итоговое состояние хранилища после прогона: `bot.outbound_messages` — 4 в
состоянии `sent`; `reminders.reminders` — 2 в состоянии `handed_off`;
`bot.recipients` — 1 получатель в состоянии `active`.

## 3. Как повторить

```bash
E2E_ADMIN_DSN="postgres://postgres:devonly_pg_admin@127.0.0.1:5433/postgres" \
  bash test/e2e/run.sh
```

Скрипт сам создаёт базу `vovremya_e2e`, роли и схемы по
`deploy/postgres/init/01-init.sh`, применяет миграции обоих сервисов, поднимает
процессы, прогоняет три сценария (`main`, `bot-down`, `bot-recovered`), проверяет
права и печатает итоговое состояние. Журналы сервисов остаются в рабочем каталоге.

Вариант с Docker (в среде разработки не выполнялся — Docker отсутствует):

```bash
make e2e-services
```

## 4. Наблюдения

1. Последовательность вызовов совпала с описанной в `docs/architecture/sequences.md`:
   reminders захватывает напоминание с арендой, вызывает bot с deadline 2 с,
   отмечает `handed_off` только после подтверждения.
2. Ключ идемпотентности формируется reminders-service, а проверяется bot-service;
   разные значения `not_after` при одном ключе дают `ALREADY_EXISTS` — это
   корректное поведение контракта, поэтому core-service должен формировать
   `not_after` детерминированно (замечание передано в handoff core-service).
3. При остановленном bot-service reminders-service не накапливает ошибок в
   плане: напоминание остаётся `planned` и берётся следующим тиком планировщика.
4. Остановка bot-service во время работы воркера доставки не теряет сообщений:
   текущее доводится до конца, остальные захваченные возвращаются в очередь
   без расхода попытки (тест `TestShutdownReleasesClaimedMessages`).

# Часть 2. Интеграция трёх сервисов (этап 3, 24.09.2026)

После реализации core-service проверена совместная работа всех трёх сервисов на настоящих
процессах и реальной PostgreSQL: `bash test/e2e/run.sh` (стенд `test/e2e/run.sh`,
сценарии `test/e2e/main.go` и `test/e2e/core_cases.go`). Docker в среде проверки недоступен,
поэтому процессы запускались напрямую; состав `compose.yaml` проверен статически
(`python3 scripts/check_compose.py`, 125 проверок).

## 1. Межсервисные контракты

| Вызов | Инициатор | Получатель | Когда | Проверено |
|---|---|---|---|---|
| `IngestService.ApplyEvents` | core (relay) | reminders | после фиксации изменения; повтор по расписанию | да, сценарий `core` |
| `ReminderQueryService.GetNextReminders` | core | reminders | реестр и карточка документа | да, шаг 6 сценария `core` |
| `ReminderQueryService.GetDocumentPlan` | стенд | reminders | контроль плана | да |
| `MessagingService.EnqueueNotification` | reminders | bot | наступил срок напоминания | да, шаг 7 |
| `MessagingService.EnqueueNotification` | core | bot | принято приглашение (`mj:<uuid>`) | да, автономные тесты core |
| `MessagingService.GetRecipientStatus` | core | bot | `GET /me` | да, сценарий `core-bot-down` |
| `MessagingService.GetBotProfile` | core | bot | создание приглашения | да, сценарий `core-bot-down` |

## 2. Проверенные сценарии

| Сценарий | Что проверяется | Результат |
|---|---|---|
| `main` | события по контракту → план → напоминание → сообщение в канале MAX, идемпотентность, webhook | пройден |
| `core` | сессия по подписанным `initData` → организация → документ → событие в reminders → план → сообщение в bot → пересчёт плана при изменении → экспорт ICS → снятие плана при удалении | пройден |
| `core-pending` (T-CONS-01) | reminders остановлен: документ создаётся, реестр работает, состояние плана не выдаётся за актуальное | пройден |
| `core-recovered` | после запуска reminders relay доставляет накопленные события, состояние становится `actual` | пройден |
| `bot-down` | напоминание остаётся в очереди, повторов без доставки нет | пройден |
| `core-bot-down` | CRUD документов работает, `reminders_channel.state = unavailable`, приглашение отвечает 503 `DEPENDENCY_UNAVAILABLE` | пройден |
| `bot-recovered` | накопленные сообщения доставляются после восстановления | пройден |

## 3. Изоляция данных

Проверено на работающей базе: `core_app` не читает схемы `reminders` и `bot`;
`reminders_app` не читает схему `core`; `bot_app` не читает схему `reminders`;
роли приложений не изменяют историю миграций; межсервисных внешних ключей — 0.

## 4. Фактическое состояние хранилища после прогона

`bot.outbound_messages`: все сообщения в состоянии `sent`; `reminders.reminders`:
`handed_off` и `planned` по действующим документам, `cancelled` по удалённому;
`core.outbox_events`: все события в состоянии `sent`.

## 5. Ограничения проверки

Docker в среде недоступен — команды `docker compose up -d --build`, сборка образов
и запуск через Compose не выполнялись. Вместо них: статическая проверка состава
`compose.yaml`, сборка и запуск тех же бинарников напрямую, применение тех же миграций
и те же переменные окружения. Режим `BOT_MODE=live` с настоящим MAX Bot API не проверялся:
токен выдают организаторы (задачи MAX-01, MAX-02 дорожки A).

# Часть 3. Интеграция мини-приложения с тремя сервисами (этап 4, 24.09.2026)

Мини-приложение проверено против **настоящих процессов** core, reminders и bot на реальной
PostgreSQL. Стенд поднимается скриптом `scripts/run_local_stack.sh` (роли, схемы, миграции,
три сервиса, готовность по `/readyz`). Проверки выполняет набор
`frontend/test/integration/api.int.test.ts`: он вызывает **тот же код мини-приложения** —
API-клиент `src/api/client.ts` и функции экранов `src/features/*/api.ts`. Подмены сетевого
слоя (MSW) в этом наборе нет.

## 1. Результат

20 сценариев, все пройдены (журнал — `docs/implementation/integration-frontend-run.md`,
таблица — `docs/testing/frontend-test-report.md` §3). Подтверждено фактическое изменение
состояния backend: организации, документы, периоды, участники, приглашения, настройки,
экспорт, удаление.

## 2. Проверенные цепочки

| Цепочка | Что подтверждено |
|---|---|
| Mini App → core | сессия по подписанным `initData`, отказ при подделке, все CRUD-операции, версия и идемпотентность |
| Mini App → core → reminders | документ создан → событие доставлено → `reminders_state` перешёл в `actual`, `next_reminder_at` заполнен |
| Mini App → core → bot | принятие приглашения → сообщение владельцу появилось в канале MAX (режим stub) |
| Mini App → core → выдача файла | одноразовая ссылка экспорта отдаёт корректный `BEGIN:VCALENDAR` |
| Роли | наблюдатель получает `FORBIDDEN`, владелец меняет роли и исключает участника |

## 3. Изменения backend, потребовавшиеся для интеграции

Кода сервисов не менялось. Единственное изменение окружения — в скрипте локального стенда
подняты ограничители частоты core (`CORE_RATE_ACCOUNT_RPS` и соседние), поскольку набор
проверок выполняет запросы пачками с одного адреса. В `compose.yaml` и на стенде MAX
действуют значения по умолчанию.

## 4. Что не проверено

Запуск через Docker Compose (Docker в среде отсутствует), браузерные сценарии Playwright
(браузеры не загружаются), работа внутри клиентов MAX (нужен токен и домен). Подробности —
`docs/implementation/known-limitations.md`.
