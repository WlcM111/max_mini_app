# Задание: bot-service в архитектуре 2.0.0 (к реализации)

Версия 2.0.0. Документ описывает изменения относительно задания v1.0.0 (`docs/handoffs/bot-service.md`),
которое остаётся действующим во всём, что не перечислено ниже.

## 1. Что меняется

| Изменение | Причина |
|---|---|
| Вызывающих сервисов два: core-service (member_joined, статус получателя, профиль бота) и reminders-service (напоминания) | ADR-017 |
| gRPC-сервер слушает только адрес внутренней сети data (10.77.2.10:9090), имя `bot-grpc` | ADR-029 |
| Комментарий поля `text` в messaging.proto приведён к спецификации: обычный текст, параметр format не передаётся | дефект 5 прежнего анализа |
| Ответ-подсказка на произвольный текст сохраняется с `kind='help'` | дефект 8 прежнего анализа |
| Запуск с `BOT_MODE=stub` при `APP_ENV=prod` запрещён | ADR-031 |
| Тестовый двойник bot для автономной проверки reminders-service находится в `services/reminders/test/botdouble` | ADR-031 |

## 2. Что не меняется

Контракт `vovremya.bot.v1.MessagingService` (номера полей, имена RPC, сообщения и перечисления),
схема `bot`, очередь доставки, дедупликация по ключу идемпотентности, состояния получателей,
ограничения скорости, обработка webhook, владение токеном бота.

Бизнес-правила сроков напоминаний в bot-service не переносятся: сервис получает готовый текст,
кнопку и предельный срок отправки.

## 3. Требования к приёму заданий от reminders-service

| Свойство | Требование |
|---|---|
| Ключ идемпотентности | `rem:<period_id>:<account_id>:<days_before>`; повтор возвращает прежний notification_id и duplicate=true |
| Предельный срок | `not_after`: сообщение позже этого момента не отправляется, переходит в expired |
| Кнопка | одна кнопка с `open_app_payload=doc_<document_id>`; форма ссылки определяется режимом bot |
| Ошибки | UNAVAILABLE и RESOURCE_EXHAUSTED при перегрузке или недоступности; INVALID_ARGUMENT при нарушении контракта |

## 4. Порядок реализации

1. Каркас сервиса на общем техническом каркасе `internal/platform`.
2. Схема bot и миграции, включая отзыв прав приложения на историю миграций.
3. gRPC-сервер MessagingService, очередь и воркер доставки с арендой.
4. Клиент MAX API, режимы stub и live, обработка webhook в транспортном адаптере.
5. Состояния получателей, ограничения скорости, метрики.
6. Тесты: контрактные по .proto, интеграционные с PostgreSQL, отказные и конкурентные.

## 5. Definition of Done

Оба вызывающих сервиса обслуживаются; повтор с тем же ключом не создаёт второго сообщения;
просроченные задания не отправляются; gRPC недоступен из сети edge; production-заглушек нет.
